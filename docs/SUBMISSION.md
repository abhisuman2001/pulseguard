## Inspiration

Medical devices are adding AI fast: smart alarms, waveform classifiers, closed-loop suggestions. Everyone asks whether the model is accurate. The question that matters at the bedside is different: *what happens to the patient when the model is wrong, slow, hung, or compromised?* Mechanical ventilation is the clearest case. The control loop literally breathes for someone, and the AI that could make it smarter is the least predictable code on the box. We wanted to show that you don't have to choose between AI and safety if the OS can **enforce** the separation.

## What it does

PulseGuard ventilates a simulated patient with pressure-controlled ventilation, running a **1 kHz control loop** on QNX 8.0. Next to it, an **AI advisor** estimates the patient's lung mechanics (resistance and compliance) every breath and classifies the condition (normal, circuit leak, occlusion, stiff lung, disconnect) with **95.2%** held-out accuracy. It suggests setting changes, which a clinician can accept from a live dashboard.

Then we attack it, live, from the dashboard:

- **CPU stress:** priority-55 busy loops on every core except 0, *including the control loop's core*. Control jitter: **TBD µs p99 → TBD µs p99**, no deadline misses.
- **Rogue AI:** the model enters an infinite loop and emits lethal proposals (PIP 80 cmH₂O, NaN rate). The kernel demotes it from priority 30 to 5 when its sporadic budget runs out. The safety envelope clamps the proposals, and the watchdog kills and restarts it. The patient doesn't notice.
- **Kill the controller:** heartbeat pulses stop, the watchdog detects it in **TBD ms**, and a new controller is breathing again in **TBD ms** with the clinician's settings restored. During the gap, the plant's independent fail-safe holds the patient safe.
- **Patient faults:** leak, occlusion, stiff lung, disconnect. Alarms within one 1 ms tick, and the AI names the problem and proposes a lung-protective correction.

## How we built it

Six QNX processes, each with one job and one criticality level:

- **`pg_sensord`**: simulated ventilator hardware as a **resource manager** at `/dev/pulseguard/plant`. One `devctl(__DIOTF)` message pass per tick sends the blower command and returns the newest sample. It can be swapped for a real I²C/PWM driver with no controller change.
- **`pg_controld`**: the safety-critical loop. **`timer_create` + `SIGEV_PULSE_INIT`** wake-ups, `SCHED_FIFO 60`, pinned to a core with **`ThreadCtl(_NTO_TCTL_RUNMASK)`**, `mlockall`, jitter measured every tick with **`ClockCycles()`**. A single hard safety envelope clamps every input (clinician or AI).
- **`pg_aiguard`**: the AI, under **`SCHED_SPORADIC`** (2 ms budget per 10 ms, priority 30, demoted to 5). It measures itself with a **per-thread CPU clock** and observes its own demotion via **`sched_curpriority`**. Telemetry is mapped **read-only**, and it can only *propose* through **`MsgSend`** to a validating server.
- **`pg_watchdogd`**: spawns everything (**`posix_spawn`**), supervises with **heartbeat pulses**, and measures detection and recovery time.
- **`pg_telemetryd`** and a dependency-free Python/JS **dashboard** that looks like a ventilator monitor.
- Least privilege with **`procmgr_ability`** (spawn and fork denied and locked), and **`slog2`** logging throughout.

Priority inheritance through QNX message passing is what makes the design safe without extra machinery. A low-priority client's request runs at the *client's* priority, so the AI and the network can talk to the controller all they like and never borrow its urgency.

Everything that isn't OS-specific (lung model, controller, safety envelope, estimator, classifier, protocol) lives in a portable C core with **38 host unit tests in CI**. The AI's training data is generated by *the same plant and controller code that runs on QNX*, and `make model` reproduces the weights exactly.

**QNX evidence:** see the "QNX evidence map" table in the README for the file and function behind each feature. Target: QNX 8.0 on QEMU x86_64 (`mkqnximage`), toolchain `qcc -V gcc_ntox86_64`. It also builds for `aarch64le`.

## Challenges we ran into

- **Adaptive Partitioning isn't in QNX 8.0.** Our first design budgeted the AI with APS. QNX 8.0's new kernel dropped it, so we rebuilt the isolation on `SCHED_SPORADIC`, runmasks, per-thread CPU clocks and priority inheritance. The result is arguably a cleaner, more POSIX design.
- **Keeping the dashboard alive under a deliberate CPU storm** without cheating: the storm saturates the control loop's own core, but leaves core 0 for the network stack.
- **Honest timing:** measuring lateness against the *ideal* time `t0 + k·period` (not the previous tick) so drift can't hide, and comparing against the *same* loop on Linux (`rtbench`) on the same host.

## Accomplishments we're proud of

- The AI can be arbitrarily wrong or hostile, and the worst it can do is waste idle CPU.
- Over-pressure is handled within **one control tick**, which is unit-tested.
- A tutorial ([Codelab](docs/codelab/README.md)) that takes a Linux developer from zero to a supervised, sporadic-fenced, 1 kHz QNX system in an hour.

## What we learned

QNX's message-passing model gives you a correct priority picture across process boundaries for free, and resource managers make "simulated hardware" and "real hardware" the same thing to the application.
